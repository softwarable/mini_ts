      6. Native forms with data-fetch

      The form keeps its normal action and method. data-fetch sends it with fetch and swaps the reply into data-target. Without JavaScript it still works as a plain form.

      • Type one letter, press Save. The browser's own minlength check stops it. mini only runs on submit, which the browser never fires, so nothing appears in the log.
      • Clear the field, press Save. The server answers 422 with the form plus an error message. Because of data-swap-error="422", that HTML replaces the form (other error codes would not be swapped).
      • Type a name, press Save. POST /demo-api/items, with the CSRF header and the clicked button's op=save.
      • Type a name, then press Enter twice quickly (or double-click Save). Saving is slow on purpose. The form is dimmed while pending (form[data-loading]), and the log shows only one POST: a write that's still running ignores repeat submits.
      • Press Preview. The button's formaction and formmethod win, so it's GET /demo-api/items/preview?name=….
      Show the HTML 
      <form action="/demo-api/items" method="post"
      data-fetch                  <!-- use action + method above -->
      data-target="#item-form"    <!-- where the reply goes -->
      data-swap="outerHTML"       <!-- replace the whole form -->
      data-swap-error="422">      <!-- also swap 422 replies -->
  <input name="name" minlength="2">
  <button name="op" value="save">Save</button>
  <button formaction="/demo-api/items/preview" formmethod="get"
          name="op" value="preview">Preview</button>
</form>

      7. Errors, redirects and security

      What happens when the server says no, redirects, or a URL points to another site. Watch the request log at the bottom.

      Not swapped: the box below keeps its content. mini:error fires (the toast). The server redirects to /demo-api/login. mini sees response.redirected and sends the whole page there, instead of putting a login page inside the box. Also a redirect, but this button's mini:redirect listener calls preventDefault(), so the redirected reply is swapped in normally. Refused before sending. Nothing leaves the page, so the CSRF token can't leak.
